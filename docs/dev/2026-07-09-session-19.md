# Session 19 — CX-6: empty mock attempts still scored nonzero after CX-3

## Context
CX-6 (follow-up on CX-3/PR #4 and CX-4/commit `abf9a1b`) reported two
remaining defects from a live run (CX-5):
1. `ssh ckad9043` → `kubectx` looks identical whether or not you connected —
   grading doesn't seem to care about SSH host/kube-context at all.
2. Submitting a mock exam with **zero** typed commands still scored
   non-zero, despite session 17's answer.json fix for vacuous
   `clusterState`-only checks.

## Root cause (the real one)
Session 17's fix (and its regression test, `tests/mock-empty-attempt.test.ts`)
only modeled `evidence.clusterState` on an empty attempt — it passed
`files: {}`, which is **not what a real empty attempt looks like**.

In reality, `collectCourseFiles()` (`src/sandbox/evidence.ts`) walks the
*entire* `/opt/course` tree and dumps every file's content into
`evidence.files`, unconditionally — including the pristine starter YAML
(`exams/mock/N/course/p<Q>/...`) that `seedCourseFromExam()` copies there
*before the student types anything*.

`evalResourceCheck`'s text-fallback path in `src/client/scoring/checks.ts`
("resource may have been created then deleted — check the student's
manifests/history instead") does a raw substring match of the check's
literal (`equals`/`contains` value, or the last path segment) against
**all** of `evidence.files` joined together. On an untouched attempt this
fallback fires for every resource check that *doesn't* find a live match,
and the starter YAML very often already contains the target literal —
because it's the "before" picture of the exact resource the question asks
you to edit:
- mock/1 Q1: starter `project-23-api.yaml` already has `containerPort: 80`
  and the Deployment name `project-23-api` → the `tcpSocket.port equals 80`
  check passed vacuously (verified via a throwaway repro:
  `evaluateChecks` scored Q1 at **25%** with zero commands, zero live
  resources, just the untouched starter file in evidence).
- mock/2 Q9: starter `legacy-ingress.yaml` ships a comment *"Rewrite it to
  networking.k8s.io/v1"* — the string `networking.k8s.io/v1` is a substring
  of that comment (and of the pre-fix `apiVersion: networking.k8s.io/v1beta1`
  itself), so `fileContains: 'networking.k8s.io/v1'` passed without the file
  ever being touched.

A second, related bug: `evidence.files` is a single flat map shared across
**all** questions — `checks.ts` joined every file's content into one
`fallbackText` blob regardless of which question was being graded, so a
literal from question 5's authored file could vacuously satisfy question
3's check. This is the actual "wrong context/question shouldn't earn
points" gap named in the issue — not an SSH/kube-context problem per se
(each question already has its own uniquely-named namespace, checked via
`initialNamespaceForQuestion`), but a text-fallback cross-contamination bug.

## Fix
`src/sandbox/evidence.ts`:
- `collectCourseFiles(examId)` now excludes any `/opt/course` file whose
  content is still byte-identical to the shipped seed
  (`exams/<group>/<examId>/course/...`, resolved via the sanctioned
  `resolveExamPaths()` — never hand-built). Exported `courseSeedDir` /
  `isUnmodifiedSeedFile` as small, independently testable pure functions.
  This closes both vacuous-pass classes above without touching individual
  `answer.json` checks: an unedited starter file (or an in-place edit target
  the student never opened) simply isn't visible to the grader at all,
  which is the correct semantics either way.

`src/client/scoring/checks.ts`:
- `evaluateChecks`'s `fileText` now only pulls in `opt/course/p<questionNumber>/`
  files for the question being graded (plus unscoped `home/*.yaml`, which
  can't be attributed to one question since `$HOME` is shared across tabs —
  see `src/ws/terminal.ts`). Closes the cross-question fallback
  contamination.

## Tests
Extended `tests/mock-empty-attempt.test.ts`:
- New case per mock: seed `evidence.files` from the exam bundle's real
  `course/` directory (i.e. exactly what's on disk right after
  `seedCourseFromExam`, before any student action), run through the same
  seed-exclusion filter `collectCourseFiles` applies, and assert the score
  is still 0%. This is the first test that actually reproduces an
  "untouched-terminal" attempt end-to-end (commands *and* files), unlike
  session 17's `files: {}` version.
- Two direct unit tests for `isUnmodifiedSeedFile` (byte-identical → true,
  student-appended content → false).
- Left the `sanity` throwaway repro (not committed) that proved mock/1 Q1
  scored 25% pre-fix with an untouched starter file in evidence, confirming
  the new tests exercise the real bug and not a strawman.

## SSH / kube-context (issue bullet 1) — scoped down, flagged for review
Re-verified session 18's own finding still holds: `src/sandbox/kubectl.ts`
and `evidence.ts` grade directly against `KUBECONFIG_PATH` /
`initialNamespaceForQuestion(examId, index)`, completely independent of
whatever context a candidate's terminal session is on. All three lab-host
contexts (`ckad9043`/`ckad5601`/`ckad7913`, `scripts/init-cluster.sh`) point
at the *same* cluster/user with no distinguishing default namespace, so
`kubectl get pods` genuinely returns identical results regardless of
`ssh`/context state — this part of the bug report is accurate.

Did not add a scored check for "did the student type `ssh <host>`" —
that would contradict `checks.ts`'s stated design contract ("assert
requirements from the question... never solution-specific choices... so any
correct solution path passes"): a candidate who runs
`kubectl --context=ckad9043 ...` without ever typing the bare `ssh` command
solves the question exactly as validly as one who does. And since each mock
question already owns a uniquely-named namespace
(`exam-q<N>`, enforced via `sanitizeNamespaceSegment`/`questionNamespace`),
there is no actual scoring exploit from picking the "wrong" context — you
cannot accidentally satisfy question 3's checks by creating resources while
on question 5's host, because the checker always reads
`initialNamespaceForQuestion` for the question being graded, never whatever
namespace/context happens to be current in the terminal.

Given the single-kind-cluster constraint that session 18 explicitly
descoped ("no second VM or cluster available... too heavy for us —
skipped"), making `ssh`/kube-context observably change `kubectl` output
would require either per-host default namespaces (doesn't fit — each host
already fans out to several `exam-q<N>` namespaces) or genuine multi-cluster
simulation (out of scope per that prior decision). Flagging this
explicitly rather than bolting on a contrived SSH-command check — worth an
explicit product call before more engineering effort goes here.
