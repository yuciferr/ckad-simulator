# Session 17 — Lightweight SSH + kube-context simulation (CX-4)

## Context
CX-4 (child of CX-2, mock-exam improvements): every mock question shows a
`context: "ssh ckadXXXX"` hint (`exams/mock/1|2/exam.json`), matching the
real CKAD exam's "ssh to the right host" workflow, but the hint was purely
cosmetic — typing `ssh ckad9043` in the terminal just hit the real `ssh`
binary and failed (no such host, no network). Same for kube-context
switching: the single kind cluster only ever exposed one context, so
`kubectl config use-context <name>` had nothing to switch to. No second VM
or cluster is available (`SANDBOX_MODE=kind`, one control-plane node) — the
session-15 competitive analysis against CK-X already flagged
"SSH-to-node jumphost + multi-node" as deliberately out of scope
("too heavy for us — skipped").

## What was built
Kept everything on the single existing kind cluster — no new nodes,
containers, or services.

### 1. Real, working named kube-contexts (`scripts/init-cluster.sh`)
After `kind get kubeconfig` writes the base kubeconfig, the script now reads
the base context's `cluster`/`user` refs and adds three more named contexts
(`ckad9043`, `ckad5601`, `ckad7913` — the exact hostnames already used across
`exams/mock/1` and `exams/mock/2`) pointing at the *same* cluster/user. This
runs unconditionally on every `init-cluster.sh` invocation (not just first
cluster creation), so it stays correct across `make up` re-runs. Real
context objects mean `kubectl config get-contexts` / `use-context <name>`
work exactly as they would in the actual exam — just against one physical
cluster instead of several.

### 2. Writable per-question kubeconfig (`docker/bashrc`)
Found that `/etc/kind/kubeconfig` is mounted **read-only** in the `backend`
container (`docker-compose.yml` — confirmed via `docker inspect` Mounts,
`RW=false`), so `kubectl config use-context` from inside a pty session would
silently fail (this was *already* true for the pre-existing
`INITIAL_NAMESPACE` → `set-context --current --namespace=...` line, which
has presumably been a silent no-op since the kind migration). Fixed by
copying the base kubeconfig into a writable, per-question file
(`$HOME/.kube/config-q<CKAD_QUESTION>`) at shell start — this also nicely
isolates kube-context state between question tabs, consistent with the
existing "each question gets an independent bash history/cwd" design
(`docs/archive/02-architecture-review.md`).

### 3. `ssh <host>` shell function (`docker/bashrc`)
A bash function (sourced via `--rcfile` on every pty spawn, same mechanism
the aliases/`kube_ps1` already use) that:
- Validates the hostname against `CKAD_LAB_HOSTS` (`ckad9043 ckad5601
  ckad7913` — kept in sync with the exam-content hint list via a comment).
- Real hosts: `kubectl config use-context <host>`, prints a login banner,
  then drops into a nested `bash --rcfile /etc/ckad/bashrc -i` with
  `CKAD_SSH_HOST` exported. The nested shell re-sources the same bashrc,
  which (a) skips the kubeconfig copy when `CKAD_SSH_HOST` is set (so it
  doesn't clobber the context switch just made) and (b) renders a
  `student@<host>:...` prompt instead of the usual `ckad:...` one, so it
  visually reads as a different machine while still running the same
  kubectl/kind toolchain (no VM/container hop needed — matches the CK-X
  comparison's explicit decision to skip real node SSH). `exit` restores the
  previous context and prints a "Connection closed" line.
- Unknown hostnames: `ssh: Could not resolve hostname <h>: Name or service
  not known` (mirrors real OpenSSH's error), non-zero exit.
- Already-connected guard prevents nested double-`ssh`.

### Exam content
No `exam.json`/`answer.json` edits needed — the existing `ssh ckad9043` /
`ssh ckad5601` (mock 1) and `ssh ckad7913` / `ssh ckad5601` (mock 2) hints
already match `CKAD_LAB_HOSTS` exactly (verified via grep, no other exam
file uses the `context` field). Grading is unaffected either way: server-side
checks (`src/sandbox/kubectl.ts`) run against `KUBECONFIG_PATH` directly with
their own `execFile`/`env`, completely independent of whatever context or
namespace a candidate's terminal session is on.
