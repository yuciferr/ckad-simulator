# 2026-07-29 — Session 22: Docker image/volume optimization

Backend image **910 MB → 515 MB (-43%)**, with no tool or capability removed
from the exam shell. Two genuine bugs surfaced while measuring.

## What was measured first

`docker history` on the old backend image:

| Layer | Size |
|---|---|
| `apt-get install` (incl. python3/make/g++) | **398 MB** |
| `npm ci` (with devDependencies) | **136 MB** |
| helm | 57 MB |
| kubectl | 56 MB |
| yq | 13 MB |
| node base | ~230 MB |

The two largest layers existed only to *produce* the app, not to run it.

## backend.Dockerfile — single stage → three stages

- **`tools`** downloads kubectl / helm / yq / kubectx into a staging root, so the
  runtime image gets the binaries without the `curl`/`git` download layers.
  kubectl is now verified against its published SHA-256, and yq is pinned
  (`v4.45.1`) instead of tracking `releases/latest`, which made builds
  non-reproducible.
- **`builder`** owns `python3 make g++` (node-pty is a native addon), runs
  `npm ci` with a BuildKit cache mount, compiles TypeScript, then
  `npm prune --omit=dev`. **-300 MB** of compilers, **-105 MB** of devDependencies.
- **`runtime`** installs only what the candidate's shell uses. Every tool
  survives: kubectl, helm, yq, jq, vim, git, wget, curl, bash-completion,
  kubectx/kubens, and the `k` alias with completion.

Two extras found by inspecting the result:

- `node-pty/prebuilds` ships bindings for every platform — the two **win32**
  ones are 24 MB of a 27 MB package, unreachable from a Linux container. Pruned
  to `linux-*`, along with the Windows-only `third_party/conpty`. **-26 MB.**
- `helm repo add` leaves a 26 MB index cache that is stale the moment it is
  built. Dropped; Q14's own step 1 (`helm repo update`) regenerates it. **-26 MB.**

Also added: OCI labels, a `HEALTHCHECK`, and `mkdir -p /app/sandbox` (the PTY's
cwd was only created on exam start, so a terminal opened before that failed to
chdir — latent in the old image too).

Deliberately *not* done: switching to `node:22-alpine` would save ~60 MB but
swap glibc for musl and GNU coreutils for busybox, changing how `sed -i`, `date`
and friends behave inside an exam. Wrong trade for a simulator. Running as
non-root was also rejected: the exam shell symlinks `/opt/course` and is meant
to be privileged, matching the real exam.

## Bug 1 — the image pre-pull never worked

`scripts/pre-pull-images.sh` ran `ctr images pull`, which writes to containerd's
**`default`** namespace. kubelet only ever reads **`k8s.io`**. Verified on the
running cluster: 7 images sat in `default`, and `k8s.io` held none of them —
so every question still pulled from the registry, while ~350 MB of unusable
duplicates sat in the node's volume forever.

Fixed with `ctr -n k8s.io`. Verified after a clean rebuild:

```
Pulled   Container image "nginx:1.25-alpine" already present on machine
```

No `Pulling` event — kubelet reused the local image, which was the entire point
of the script.

The list was also wrong: it pre-pulled `nginx:1.25` (190 MB) and
`bitnami/kubectl:1.32` (~250 MB) while *missing* `nginx:1.27-alpine` and
`nginx:1.25-alpine`, the two most-used images in the exams. Now it pulls the
eight small alpine images the questions actually lean on; heavyweight one-off
images are left to pull on demand.

## Bug 2 — mock Q14's Helm repo did not exist

Q14 tells the candidate "the bitnami repo is already added". It was being added
by `init-cluster.sh` inside the **kind-init** container — which does not even
have helm installed, and is thrown away seconds later. Helm repos are
client-side config in `$HOME`, so it could never have reached the exam shell.
`helm repo list` in the backend returned "no repositories to show".

Moved into `backend.Dockerfile`, where the exam shell actually runs. Verified.

## docker-compose.yml

- **Removed the Docker socket from the backend.** It never used it — no `docker`
  call exists anywhere in `src/` or `scripts/reset-question.sh`. Mounting it
  handed root-equivalent host access to the container that runs untrusted
  candidate input. `kind-init` keeps it; that one genuinely drives the daemon.
- **`init: true`** — every question tab forks a bash PTY, and without an init as
  PID 1 the exited shells accumulate as zombies.
- `security_opt: no-new-privileges`, `stop_grace_period`, json-file log rotation,
  explicit `image:` names, and a YAML anchor for the shared build args.

## kind-init.Dockerfile

Collapsed to a single layer, added checksum verification for kubectl and OCI
labels. Size is unchanged (112 MB) — it is two Go binaries plus docker-cli, with
nothing to strip.

## Verified after a full `down -v` + clean `./install.sh`

Cluster ready; all 12 shell tools present at the right versions; bitnami repo
listed; the three `ssh` lab-host contexts provisioned; `make reset-q Q=3` applies
the scenario; a pre-pulled image starts with no registry round-trip; node-pty
spawns a real `/dev/pts` TTY after the prebuild pruning; and an end-to-end
WebSocket session runs `kubectl get deploy -n exam-q3` and returns output.
`build`, `lint`, `test` (26/26), `validate:exams`, `validate:scenarios` all green.

## Remaining / next

- `git` is the largest single runtime package (~19 MB compressed, ~45 MB
  installed). Nothing advertises it as a feature and the real exam does not
  guarantee it — dropping it would take the image to roughly 470 MB. Kept
  because removing a working shell tool is a user-visible regression.
- `kindest/node:v1.32.3` (1.06 GB) and the cluster's containerd volume (~2 GB)
  are dominated by Kubernetes' own system images (etcd, apiserver, kube-proxy).
  That floor cannot move without changing the Kubernetes version.
- Local build cache had grown to 9.58 GB during this work — `docker builder
  prune` is worth mentioning to users at some point.
- Still no CI. A workflow that builds both images and runs the gate would catch
  exactly the kind of drift found in this session.
